# Extra evaluation axes for the MAE matrix

What gets added to BABEL-60 window classification, in what order, and why each
decision went the way it did. Settled 2026-09-18. Scope is the **MAE branch only** --
JEPA and SimMIM are out until this lands, because half of what is below cannot be
computed for an objective that reconstructs nothing.

Today the matrix is ranked by two numbers: the convex probe
(`results/probe/babel_60_convex/`) and the fine-tune (`results/finetune/babel_60_finetune/`).
Both are window-level multi-label mAP, and window-level mAP is weakly discriminative:
a linear model on the mean, std, min and max of each channel reaches 94% of a
pretrained probe there. The cells this report ranks differ by 0.003-0.010 macro mAP.
That is the problem every axis below is trying to get around.

## Standing rules

These apply to every task here and are not restated per phase.

**Cells and seeds.** 3x3 (`p`/`pk`/`pkd` on both the input and loss axes) x 3 seeds,
the same nine cells `finetune_matrix.sh` selects with `CELLS`, so every ranking is
comparable to the fine-tune table row for row. Three seeds is not negotiable:
`results/decoder_capacity/README.md` reported 9.5 sigma from a single seed draw with a
borrowed sigma, and it did not survive replication. That page is the standing warning.

**Dumb baseline in the same table.** Every task publishes its floor beside it, on the
same split, in the same unit -- moments for the classification-shaped tasks
(`scripts/moments_baseline.py`), zero-velocity and constant-velocity for forecasting.
A gap to the floor that sits inside the seed spread is reported as such, not quietly
omitted. Everything gets reported either way.

**Reporting convention.** Existing shape, unchanged: `README.md` + `gen.py` +
`metrics.csv` + `baselines.json` + `figures/`, with the `<!-- GENERATED by gen.py -->`
marker and hand-written prose above it. Each phase gets a matrix runner mirroring
`scripts/probe_matrix.sh` -- same `CORPUS`/`ARCH`/`EPOCHS`/`OBJECTIVE`/`SEEDS` knobs, same
`done`-marker check, same `metrics.json` skip.

**Three destination directories**, split by what they rank rather than one per task:

| dir | holds |
| :--- | :--- |
| `results/representation/` | effective rank, CKA, label-efficiency, kNN |
| `results/probe/babel_60_segmentation/` | the segmentation probe |
| `results/reconstruction/` | reconstruction and forecasting -- one rig, one decoder, two masks |

`results/representation/` is three measurements sharing one feature extraction pass.
The extraction rig is built in phase 0 and reused in phase 2; the directory grows rather
than being written once.

## Phase 0 -- Representation geometry

Cheapest thing here and it runs first, because it can invalidate a later table before
that table is measured: if a cell's pooled features are near rank-1, every task score
for that cell is explained before anyone scores it. No labels, no head, no baseline, one
pass over features the probe already extracts.

- **Statistic**: participation ratio, `(sum lambda)^2 / sum lambda^2`, on the pooled
  features the convex probe actually fits -- same tensor, same parameter-free
  `LayerNorm`. It explains that exact table and nothing else, which is the point.
- **CKA**: all-pairs across the nine cells, with one cell's cross-seed CKA printed as the
  noise floor. That is how the existing 0.934 (cross-cell) against 0.959 (cross-seed)
  comparison was read, and it stays readable the same way.
- **Build note**: CKA exists in this repo only as a stored number in
  `results/decoder_capacity/evidence.json`. There is no gram matrix, no HSIC and no rank
  statistic in any module. This is new code.

## Phase 1 -- Action segmentation

The real build, and the one that attacks window classification's actual weakness. The
target varies inside the window, so order-invariant summary statistics cannot reach it.

`src/sometria/downstream/segmentation.py` and `config/experiment_segmentation.yaml`
already exist and are correct in design. What does not exist: any script that trains
`MotionSegmenter`. `train.py` registers `mae`/`jepa`/`simmim` only. The config also pins
a dead checkpoint (`runs/ablation_long/pretrain/seed_13/...`) rather than the matrix tree.

- **Head**: convex. `mean` pooling over the **DOF axis only** -- the time axis survives, so
  a window becomes `30 x d_model`, one vector per time patch, never one vector per window.
  Per-patch BCE over a parameter-free pooling is still per-label logistic regression, so
  the whole L-BFGS + weight-decay-sweep rig from `classifier_convex.py` transfers with
  rows `(window, patch)` instead of `(window,)`. `moments` pooling was considered and
  rejected: mean is what is wanted here.
- **Why not the AdamW/attentive head that is already written**: it is non-convex, and a
  ranking whose cell gaps are 0.003-0.010 cannot afford a head that also varies with lr,
  warmup and epoch budget. The `readout_ablation.md` gap (attentive 0.341 vs mean 0.289)
  does not transfer -- it measures pooling all `T x D` tokens into one vector, and most of
  what attentive buys there is choosing which *time* patches matter, which is precisely
  the axis this task keeps instead of pooling.
- **AdamW + attentive stays available** as a second, optional test -- the ceiling run, not
  the ranking instrument. It is the only fine-tuning left in this plan.
- **train_passes = 20**, matching the window probe's `DEFAULT_TRAIN_PASSES`. This was first
  settled at 2 on a memory argument that was wrong: it assumed ~9k usable windows, forgetting
  the `source_datasets: ["AMASS"]` filter. Measured, `babel_official/train` is 12,994 samples
  -> 10,015 at >= 240 frames -> 4,903 after the AMASS filter -> 3,488 carrying frame-level
  `act_cat` -> **3,282 usable train windows**. That is 0.32 GiB of features at 2 passes and
  1.88 GiB at 20, so memory does not decide this.

  What decides it is that there is no saturation point to find. Passes buy distinct random
  crops, and the median eligible sample has **278 distinct window offsets** -- only 3.6% of
  samples have 20 or fewer. So 2 passes touches 0.7% of the crop space and 20 touches 7.0%:
  both small, the curve between them smooth and monotone, and a sweep over passes would only
  confirm that more data helps. With no knee to exploit, the tie is broken by comparability --
  segmentation's table is read beside the window probe's, and a different passes count would
  add a second axis of difference between them. Cost is extraction: frozen forward passes, no
  backprop.

  The asymmetry to keep in mind: at equal passes segmentation already yields 30 rows per
  window against the window task's 1, so matching the passes number does not match the
  supervision. 20 is a default, not a derivation.
- **Ranking number**: per-patch macro mAP, on the same scale as the published window mAP.
  **Gate**: `boundary_f1`, reported beside it. A prediction constant across the window can
  still score on mAP and scores zero on boundary F1, so a cell that beats moments on mAP
  but not on boundary F1 has not demonstrated temporal structure, and the README says so
  in words.
- Data settings come from the existing config and are not revisited: `label_min_coverage`
  0.5, `label_types: ["frame"]`, 240-frame windows, 30 time patches, boundary rate 0.080.

## Phase 2 -- Label efficiency and kNN

Both refit or read the phase-0 features. Extraction dominates the bill and is already paid.

**Label-efficiency curve.** Refit the convex head at 5 / 10 / 25 / 50 / 100%.

- Subsample by `sample_id`, never by window. Windows are crops of samples, so 1% of
  windows still touches nearly every sample and its neighbours' crops.
- Every fraction is scored on the **same label set** -- the labels present at the smallest
  fraction. Otherwise `WindowMeanAveragePrecision` drops zero-support labels and the 5%
  number is a macro average over a different vocabulary than the 100% number, which makes
  the curve five metrics rather than one.
- Validation split is never subsampled.

**kNN retrieval.** `scripts/knn_probe.py` already specifies everything: cosine similarity,
softmax-temperature weighting (Wu et al., as used by MoCo and DINO), a sweep over k, and
the probe's own metric set. It needs a matrix runner and nothing else. A backbone that
ranks well here and badly under a linear head is saying something specific, which is the
reason it is worth the near-zero cost.

## Phase 3 -- Reconstruction (diagnostic, not a ranking)

**Reconstruction does not rank cells.** Pre-registered, in the README, before the table:
better representations often reconstruct *worse*, because a near-identity encoder passes
everything through and decodes beautifully while abstracting nothing. This matrix already
hints at it -- `loss_p` cells reconstruct the easiest target and probe worst (0.3446
against 0.3734). If the degrees column ranks the nine cells inversely to BABEL mAP, that
is the expected result and it is written down here first so it cannot be discovered after
the fact.

Each cell's own pretraining loss is *not* the metric. `loss_p` scores 2 channels,
`loss_pkd` scores 5, and `norm_targets` standardizes per token, so those numbers are not
on one scale and never were.

- **Rig**: frozen backbone, one identical freshly-trained decoder per cell.
- **Decoder**: `tinydec`, `dec_depth 1` / `dec_dim 64`, about 0.4x encoder FLOPs, identical
  for every cell and shared with phase 4. This is the confound that already bit this
  project: `medium`'s pretraining decoder runs at 8.6x the encoder's FLOPs and can compute
  torque itself from kinematics (a linear map recovers R^2 = 0.685), which is the standing
  explanation for why the `pkd` loss channel looks inert. A probe decoder that size would
  rank decoders rather than backbones. Same reasoning as segmentation refusing a temporal
  layer before its head.
- **Target**: `sin, cos` only -- the channels every cell has -- scored as **mean per-DOF
  angular error in degrees** after `atan2`. One scale, one physical unit, readable.
- **Mask**: `mask_ratio = 0.75`, uniform (`random_mask`, which is what `tau <= 0` means), identical for every cell, both stated
  in the README. Off pretraining's 0.90 on purpose, so the number is not each cell's own
  training objective wearing a new name. Uniform because motion-aware masking would draw
  the holes from a per-cell config and hand different cells different-difficulty windows.

## Phase 4 -- Forecasting, ~1 s

The same rig as phase 3 with one mask changed, which is why it shares a directory and a
decoder rather than being a separate build.

- **Mask**: the last **8 time patches** of the existing 240-frame window, across all 43
  DOFs, as a fixed index set handed to the same `(keep, mask)` scatter path
  `baseline.Decoder.forward` already takes, instead of a random draw. Note the tree does not
  match CONTEXT.md here: there is no `models/window.py`, no `mask_window` and no
  `MaskedWindow`; masking is `baseline.random_mask` and flat index pairs, and `MaskSpec` in
  `masking.py` is imported by nothing. 8 patches x
  8 frames = 64 frames = **1.067 s** at 60 Hz, reported as "~1 s". 1 s exactly is 7.5
  patches and does not exist.
- **Why not a longer window**: a 300-frame window means a new `min_frames`, a smaller
  eligible sample pool and a new collate, to buy a horizon that the existing window
  already contains.
- **Backbone frozen**, `tinydec` trained. Fine-tuning would make the ranking "how well this
  init trains a forecaster" rather than "what this representation already carries" -- and
  the first of those is already on disk as `babel_60_finetune`.
- **Unit**: degrees, same as phase 3.
- **Baselines**: zero-velocity (hold the last observed frame) and constant-velocity
  extrapolation, same unit, same split. Non-negotiable here: at 60 Hz much of a 1 s horizon
  is predictable from the last two frames, so without these a forecasting MSE table cannot
  distinguish a good backbone from an easy horizon.

## Considered and not doing

- **Noise-robustness** (perturb channels, measure mAP decay). Cheap, but it needs its own
  baseline and would be dropped before anything above.
- **CARE-PD transfer as part of this effort.** `results/probe/carepd_updrs_convex/` already
  exists across 126 protocol split sets and is zero build. Deliberately out of scope here.
- **Physical plausibility** (foot skate, torque consistency). Needs an OpenSim round-trip,
  and measures decoder quality more than encoder quality.
- **In-betweening.** A third mask over the phase-3 rig, carrying no information beyond
  what the suffix mask already gives.

## Open assumptions

- The fine-tuning budget approved at the start of this discussion goes almost entirely
  unused. Phase 1's attentive/AdamW ceiling run is the only fine-tuning in the plan, because
  every other axis was better answered frozen. This is a real narrowing of what was approved.
- Cell coverage is 3x3, not the published 4x4. The `pv` row and column are not scored by any
  task here.
- **Phase 0 is measured on the validation split, not the training features the convex probe
  fits.** Departure from this document as first written, forced by CKA: `LabelledWindows(tiles=False)`
  draws a random crop per sample per pass, so two cells' training features are two different
  window sets and the row correspondence CKA requires does not exist. Evaluation tiles are
  deterministic, so row *i* is the same frames in every cell by construction. Participation
  ratio is read off that same matrix so both numbers describe one tensor. The consequence to
  remember: the geometry column describes the features at evaluation time, which is what every
  reported score is computed from, but not literally the matrix the head was fit on.
